# ЭПСИЛОН — MVP

ЭПСИЛОН — рабочая система управления разработкой с тестовыми данными. Авторизация, права и планирование хранятся в PostgreSQL; финансовые, производственные и качественные реестры остаются тестовыми. Технологическая карта временно скрыта до переработки.

## Авторизация и пароли

Ветка `codex/server-authentication` заменяет открытый статический хостинг сервером Node.js + PostgreSQL. Публиковать эту версию можно только после настройки собственного HTTPS-адреса, независимых секретов ЭПСИЛОН и БД. Существующая публичная демонстрация не обновляется автоматически из этой ветки.

- `/login`: вход по email и паролю, «Забыли пароль?». Селектор демонстрационных пользователей отключён. Сессия определяется сервером, а не полем `actorId` из браузера.
- При создании пользователя сервер генерирует случайный временный пароль. Создавший видит его в отдельном окне и передаёт лично; автоматических email/SMS нет. Временный пароль действует 48 часов; до обязательной смены при первом входе рабочее пространство и его ресурсы закрыты.
- `/account` или «Сменить личный пароль» в собственном профиле: текущий пароль, новый и повтор нового. От 16 до 128 символов, поддерживаются парольные фразы. Новый пароль заменяет прежний; старые сессии завершаются, текущая получает новый идентификатор. Восстановление старого пароля невозможно.
- «Пароли и восстановление»: запросы администратору; при отсутствии доступного администратора — Суперадмину. Запрос не изменяет пароль и не подтверждает существование email внешнему посетителю. Перед выдачей нового временного пароля ответственный проверяет личность по доверенному каналу и указывает основание. Новый пароль сообщается лично вне системы.
- Администраторы сбрасывают пароли обычных пользователей, но не руководителей. Пароли руководителей сбрасывает только Суперадмин (подтверждено заказчиком). Пароль действующего Суперадмина не сбрасывается через веб-интерфейс: оператор его отдельного сервера использует `docker compose exec -it web node server/recover-superadmin.mjs`. Это интерактивная аварийная операция с подтверждением, отзывом прежних сессий и записью в аудит; общего резервного пароля нет.
- База временных паролей — только Суперадмину. В PostgreSQL копии временных паролей шифруются AES-256-GCM отдельным ключом вне БД; после смены пользователем, отключения учётной записи или истечения срока удаляются из действующего состояния. Личные пароли хранятся **только в виде scrypt-хешей** с отдельной солью (N=131072, r=8, p=1) и никогда не попадают в эту базу, API, аудит или браузерное хранилище. Исторические резервные копии БД требуют отдельной политики сроков хранения.
- Сессии: 256-битный случайный идентификатор, в БД — только его SHA-256-хеш; cookie `__Host-epsilon_session; Secure; HttpOnly; SameSite=Strict; Path=/`. Абсолютный срок 8 часов, неактивность 30 минут. Изменение/сброс пароля, блокировка, отзыв доступа, удаление и изменение профиля отзывают соответствующие сессии. Есть CSRF, проверка Origin, лимиты попыток, `no-store`, HTTPS-only в production. HTTP не принимает пароль, включая случай неверной конфигурации reverse proxy.

Первый настоящий Суперадмин создаётся один раз из `EPSILON_BOOTSTRAP_EMAIL` и `EPSILON_BOOTSTRAP_HASH`. Повторный старт контейнера не сбрасывает пароль, не создаёт новых владельцев и не восстанавливает тестовых пользователей. Для подготовки без записи открытого пароля: `node scripts/create-bootstrap.mjs EMAIL https://DOMAIN` и скрытый интерактивный ввод. Генерируется игнорируемый Git файл `deploy/.env.auth` с правами `0600`: email, scrypt-хеш, независимый случайный ключ базы временных паролей и HTTPS origin. Никогда не публикуйте этот файл или его содержимое. При ручном переносе в Dokploy сохраните одинарные кавычки вокруг хеша: `$` не должен интерполироваться Compose. Исходный пароль в контейнер не передаётся.

Ориентиры: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html). Это не сертификат безопасности и не замена независимому аудиту.

## Администрирование и модель доступа

Раздел `/admin`: пользователи, проектные и секционные допуски, доступ по инцидентам, проекты и бюджеты, структура предприятия/справочники, правила ролей и журнал изменений. Роль, должность и отдел — независимые поля. Должность не предоставляет полномочия.

### Структура предприятия и назначение сотрудников

- Руководитель управляет всей структурой. Руководитель отдела и руководитель проектов — своим отделом и его подотделами, только в пределах допущенных проектов и собственных полномочий. Администратор видит метаданные структуры, но не меняет её через этот раздел.
- Можно создать отдел/подотдел, выбрать его проекты и рабочие разделы, переименовать с обязательным основанием. Переименование сохраняет идентификатор, состав, проекты, права и историю; не используется для скрытого изменения допусков.
- В выбранный отдел можно добавить нового сотрудника с должностью и временным паролем либо назначить пользователя из списка «Роль не назначена». Через этот сценарий выдаётся только базовая роль «Сотрудник». Руководитель отдела/проектов не может повысить роль, переместить защищённые управленческие записи, затронуть чужой контур или выдать больше своих прав. Ограничение прав нового сотрудника сохраняется на сервере.
- Изменение состава позволяет перевести обычного сотрудника между доступными отделами, скорректировать должность/проекты либо исключить из отдела. Назначение существующего пользователя не выдаёт нового пароля. Исключение снимает роль и допуски, сохраняя учётную запись, пароль, авторство и историю; старые сессии завершаются. Управленческие роли настраиваются отдельно уполномоченным администратором/руководителем по прежним правилам.
- Новая запись по умолчанию создаётся без роли. Пользователь без роли, действующего отдела или допуска к проектам после обязательной смены временного пароля видит только `/pending`: «Дождитесь добавления Вашего профиля Руководителем», собственный профиль, смену пароля и выход. Списки коллег, проекты, аудит, бизнес-страницы и их JS-ресурсы сервер не выдаёт. Для допуска недостаточно просто создать учётную запись. После назначения требуется новый вход.
- Структура, состав, ограничения, основания, события и планирование сохраняются в PostgreSQL через транзакционный серверный контур. Остальные рабочие разделы остаются на тестовых данных и не переводятся этим изменением в общее бизнес-хранилище.

### Роли и полномочия

- **Руководитель · Суперадмин:** уникальное полномочие первого руководителя, а не свободно назначаемая роль. Все проекты, разделы и пользователи; создание, блокировка, отзыв доступа и удаление любых других учётных записей, включая администраторов и руководителей. Собственную запись нельзя блокировать, удалять или лишить полномочий через смену роли. Удаление закрывает доступ и убирает пользователя из рабочего списка, но сохраняет запись, авторство, задачи и документы; архив доступен Суперадмину.
- **Администратор:** добавляет и настраивает пользователей, утверждает проектные и обычные секционные допуски, блокирует/разблокирует учётные записи с обязательным основанием. Не может редактировать или блокировать ни одного руководителя. Не имеет постоянного доступа к бизнес-данным. Не меняет свою роль; роль «Руководитель» назначает только руководитель — правило подтверждено заказчиком. Не выдаёт бизнес-права руководителя проектов.
- **Руководитель:** все проекты и разделы; полный список сотрудников, сгруппированный по отделам и внутри отдела по ролям/имени. Создание/описание проектов, изменение базового планового бюджета в рублях с основанием, отделы и сотрудники, роли, ограничения и дополнительные права чтения. Может блокировать и отзывать доступ у сотрудников, руководителей проектов и руководителей отделов, но не у администраторов, других руководителей и самого себя; не редактирует чужие защищённые профили в обход этого правила. Удаление учётных записей — только у Суперадмина. Факт, обязательства и EAC не изменяются вместе с планом автоматически.
- **Руководитель отдела:** работа и верификация в разделах своего отдела и в своих допущенных проектах. Управляет своим отделом и подотделами, добавляет базовых сотрудников, редактирует должности, ведёт сущности/классификации отдела. Управленческие роли не меняет. Может настраивать права руководителя проектов своего отдела только в пределах собственных проектов и возможностей. Руководитель и руководитель отдела могут назначать задачи всем активным пользователям и менять сроки любых карточек в допущенных проектах.
- **Руководитель проектов:** роль `project_manager`, отличная от прежней демонстрационной роли `manager`. Нет автоматического доступа к бизнес-разделам своего отдела или всем проектам. Доступна ограниченная админка команды: сотрудники своего контура и структура предприятия; нет глобальных допусков, бюджетов, инцидентов, смены ролей или базы паролей. Планирование доступно на чтение в назначенных проектах. Руководитель или руководитель отдела задаёт отдельную матрицу по каждому проекту: нет доступа / чтение / изменение / верификация и отдельное право изменения сроков карточек. Изменение включает чтение, верификация включает изменение. Для управления сроками нужно также право изменения планирования. Руководитель отдела не может делегировать права выше своих или менять настройки в проектах за своим контуром; ранее назначенные полномочия вне его контура сохраняются. Управленческие роли по-прежнему назначают только администратор или руководитель, а должность указывается независимо.
- **Сотрудник:** задачи в допущенных проектах и первичные данные своего отдела. Нет сводной аналитики, бюджета, полной выгрузки и администрирования. Чужой раздел открывается только на чтение по отдельному назначению. Создание задачи не предоставляет исполнителю допуск к чужому проекту; такая карточка получает соответствующую отметку. Сроки существующих карточек изменяют руководители.

Индивидуальные режимы раздела: по роли/отделу, только чтение, нет доступа. Проектный допуск обязателен независимо от режима. Пустой допуск допустим: пользователь существует, но проектные данные ему не открыты. Верификация отделена от обычного ввода данных.

Руководитель выдаёт администратору **временный допуск только на чтение**: конкретные проекты из круга администратора, разделы, номер инцидента, основание, срок 1/4/24 часа. Может отозвать его с результатом разбора. Проверка срока выполняется при каждом действии и периодически обновляет интерфейс. Экспорт, изменение данных и переписки исключены. Администратор не выдаёт допуск себе. Блокировка и отзыв доступа перекрывают все права; старые временные допуски после восстановления не оживают. Разблокировка не отменяет предшествующий отзыв доступа. Любая операция требует основания и проверяется заново при сохранении. Действующий Суперадмин защищён от отключения и понижения роли.

**Передача Суперадмина:** вкладка «Суперадмин / передача». Владелец выбирает нового владельца из активных руководителей и третьего активного руководителя для подтверждения. Инициатор, получатель и подтверждающий — три разных человека (подтверждено заказчиком). До подтверждения полномочия не меняются. Только указанный третий руководитель подтверждает или отклоняет запрос с основанием; инициатор может отменить. При сохранении повторно проверяются статусы, роли всех троих и действующий владелец. Нельзя подтвердить устаревший/уже обработанный запрос или создать параллельный действующий. После подтверждения ровно один новый владелец, прежний остаётся руководителем. Запрос, отмена, отклонение и передача фиксируются в журнале. На первой миграции назначается первый активный руководитель; последующие загрузки не переизбирают владельца. Для демо добавлены Анна Крылова и Павел Громов как второй и третий руководители и Дмитрий Лебедев как руководитель проектов.

**Переписки:** администратор не читает никакие чаты; руководитель, включая Суперадмина, не читает чужие личные переписки 1 на 1 (подтверждено заказчиком). Участник видит свою переписку; руководитель может видеть групповые обсуждения. Эти исключения реализованы как тестируемая политика будущего модуля. **Самого мессенджера пока нет**, сообщения не создаются и не экспортируются.

В прежнем статическом демо старые роли мигрировали без удаления данных: руководитель проекта → руководитель отдела, инженер/закупки/инвестор → сотрудник с сохранением функции в должности; были добавлены демонстрационные руководители и сотрудники. Эти сценарии сохранены в тестах совместимости. **Серверная авторизация не импортирует эти профили и не создаёт им пароли:** в настоящем контуре сначала существует только настроенный Суперадмин, остальных добавляют через администрирование. Прежние локальные данные не удаляются и не дают серверных полномочий.

**Граница реализации:** вход, пароли, сессии, учётные записи, допуски и трёхсторонняя передача Суперадмина контролируются сервером и хранятся в PostgreSQL. Сервер повторно проверяет административные операции и планирование; клиентский `localStorage` не определяет роль и не является источником задач. **Планирование записывается в PostgreSQL, остальные бизнес-реестры остаются тестовыми в клиентском приложении** и не предназначены для конфиденциальных данных или операционного учёта. Полевой перевод остальных модулей, миграция локальных бизнес-записей, документы/файлы, внешняя доставка уведомлений и мессенджер остаются отдельными этапами. Перед реальной эксплуатацией также нужны HTTPS-домен, отдельные секреты и независимый аудит конфигурации.

## Планирование

- Доска Trello-типа работает в контексте проекта: Бэклог, Ожидает, В работе, На верификации, Блокеры, Завершено. В карточках нет сумм, планов или EAC; сроки, ответственный, соисполнители и описание остаются видимыми.
- Задачи доступны в пределах проектного допуска. Сервер проверяет право на изменение, активный доступ ответственного и соисполнителей, принадлежность меток проекту, иерархию и право менять сроки. Пользователь может назначить одного ответственного и нескольких соисполнителей.
- Иерархия: эпик → задача → подзадача → фикс. Задачи могут быть самостоятельными; фикс относится к задаче или подзадаче. Начало, срок и родитель хранятся для последующего построения диаграммы Ганта.
- Разовые и регулярные задачи: повторение еженедельно или ежемесячно. Регулярная задача хранится в бэклоге и активируется за заданное число дней до срока; после завершения следующая карточка создаётся автоматически. Исполнитель переводит её на верификацию.
- Теги ведутся отдельно в каждом проекте. Отдел создателя добавляется автоматически; теги сотрудников доступны участникам проекта, цвет точки меняется в настройках меток. Исторические метки не удаляются из старых задач.
- Можно задать до десяти напоминаний. Уведомления доставляются браузером, если пользователь дал разрешение и приложение открыто; фоновой доставки, email и SMS пока нет.
- При первом запуске существующей БД тестовые карточки переносятся в серверное состояние только один раз. Они остаются начальными данными для показа; старые локальные правки не импортируются автоматически.

## Производство

Раздел `/production` — оперативная сводка руководителя по одному проекту или портфелю. Демонстрационный срез фиксирован на **19.10.2026**. Периоды: день, последние 7 дней, текущий месяц, квартал или диапазон до 366 дней; график группируется по дням, неделям или месяцам. Производственный календарь независим от финансового переключателя Q3/Q4.

- Выпуск по партиям и ревизиям: проверено, годные, брак. Можно зарегистрировать новую партию с документом ОТК.
- Отгрузки: план, факт, просрочки, причины блокировки; фиксация факта с накладной и основанием допуска. Годный неотгруженный остаток считается накопительно и сам по себе не означает снятия блокера отгрузки.
- Раздельные показатели брака: производство / проверенные изделия и поставщики / проверенные комплектующие. Это взвешенные доли, а не среднее процентов; при нулевой базе отображается «—». Показатели относятся к партиям периода, реестр актов — к датам выявления.
- Фиксация брака с источником, партией/закупкой, количеством, оценкой потерь в рублях, актом, ответственным и действиями. Проверяется лимит партии, уникальность акта и остаток после уже выполненных отгрузок. Решения сохраняются в истории; закрытие акта не отменяет факт и не превращает брак в годные изделия.
- Стоимость комплектующих: отдельные суммы заказов, оплат и остатка оплаты. Реестр связан с исходными закупками; заявки без заказа и оценки техкарты не выдаются за платежи. Реквизиты поставщиков и платежи — демонстрационные.
- Сводный и отдельные отчёты по браку поставщика/производства: Word (.doc), CSV для Excel и JSON. Финансовые суммы — в тыс. руб.; снимки сохраняются в общей истории отчётов. Общие отчёты также включают производство.

Производственные данные сохраняются в существующем `localStorage`, не удаляя пользователей, карточки и техкарту. Исторические партии не являются разрешением на сборку текущей непроверенной ревизии. Производственные операции не меняют демонстрационный финансовый базис или склад компонентов. Нет интеграции с ERP/бухгалтерией, серийного учёта, фактических возвратов, загрузки файлов и общего серверного хранения. Документы — идентификаторы или ссылки. Исправление ошибочной исходной записи через сторно — следующий этап, удаления фактов из интерфейса нет.

## Технологическая карта

Раздел `/technology` показывает состав тестовой сборки выбранного проекта: подсистемы, ревизии, количество на изделие и партию, годные остатки, брак, детали в пути и готовность к сборке. В примере AURORA-02 теплоотвод и корпус готовы, датчики и жгуты блокируют сборку, GaN-модули ожидают поставки, а плата Rev D — верификации. ORBIT-01 и NOVA-03 имеют собственный состав.

Можно добавить компонент, изменить его с новой ревизией и обязательным обоснованием, запросить верификацию, зафиксировать результат с протоколом или сформировать валютную закупочную заявку. Запросы связаны с карточками канбана, бюджетными оценками, разделами закупок и качества. Прежние ревизии и основания изменений сохраняются; запросы старой ревизии требуют актуализации. Word, CSV для Excel и JSON включают состав, запросы и историю.

Это прототип: складские остатки и исходные финансовые данные — демонстрационный снимок. Запросы не меняют утверждённый бюджет, EAC, фактические расходы или наличие деталей. Брак не становится годным после успешного теста. Реальные поставки, приёмка, согласование закупок и прикрепление файлов не реализованы; поле документа хранит идентификатор или ссылку. Валютный курс в заявке — редактируемый сценарный курс, не рыночная котировка.

Канбан поддерживает добавление и редактирование карточек, перетаскивание и смену статуса в деталях карточки. Новые оценки формируют бюджетные заявки. Карточки, техкарта, производство и история отчётов сохраняются локально под отдельным ключом для вошедшего пользователя; пароли и сессии туда не записываются. Общего серверного бизнес-хранилища пока нет. Прежний `epsilon.workspace.v1` сохраняется без удаления; его административные данные не импортируются автоматически и не могут предоставлять реальный доступ.

Базовая валюта интерфейса — рубли. Word, CSV для Excel и JSON показывают финансовые суммы в **тыс. руб.**; формы ввода принимают рубли. Для демонстрационного перехода численные значения существующих бюджетов и оценок сохранены без пересчёта по рынку. Карточки, пользователи и история сохраняются, прежние обозначения базовой валюты обновляются при загрузке и повторной выгрузке. Закупки доступны в RUB и USD, итог рассчитывается в рублях по явно указанному курсу. Сценарный курс для новых заявок — 92 руб./USD, не рыночная котировка; курс старых заявок не переопределяется.

## Состав

- `dist/index.html`, `dist/assets/` — интерфейс, маршруты, данные и SVG-иконка ЭПСИЛОН;
- `server/` — HTTP/API авторизации, scrypt, шифрование временных паролей, политика полномочий и транзакционный PostgreSQL store;
- `Dockerfile` — Node.js-контейнер, работающий без root и слушающий только внутренний порт 8080; `deploy/nginx.conf` оставлен как историческая конфигурация прежнего статического прототипа и больше не используется;
- `compose.yaml` — изолированный контур из веб-сервиса и отдельной PostgreSQL-БД.

## Локальный просмотр

Выполните `npm ci --ignore-scripts`, `npm run preview` и откройте `http://127.0.0.1:4195/login`. Это полностью одноразовое окружение с MemoryStore, без настоящих секретов и без подключения к PostgreSQL. Тестовый вход: `superadmin@epsilon.test`, пароль `Local-Demo-Password-Only!`. Тест первого входа: `fixture@epsilon.test`, временный пароль `Local-Temporary-Password-2026!`. Для проверки структуры добавлены `head@epsilon.test`, `pm@epsilon.test`, `production@epsilon.test` и `pending@epsilon.test` с синтетическим паролем `Local-Organization-Password-2026!`; последний профиль демонстрирует экран ожидания без роли. Эти фикстуры существуют только в `scripts/auth-preview.mjs` и не копируются в production-контейнер. После остановки все созданные тестовые учётные записи исчезают. Не вводите сюда настоящий пароль.

Проверки: `npm test`. HTTP-тесты используют временные loopback-серверы `127.0.0.1:4197` и `:4198`; при ограничениях sandbox требуется разрешение на bind. Проверяются хеширование, невидимость личных паролей, шифрованная база временных, обязательная смена, срок, отзыв сессий, маршрутизация запросов, права администратора/Суперадмина, CSRF/Origin/rate limits, закрытие ресурсов до входа, HTTPS и прежние рабочие сценарии. Набор структуры проверяет иерархию, переименование без смены допусков, выдачу временного пароля, назначение без изменения личного, пределы делегирования, защищённые роли, исключение, аудит и полную изоляцию ожидающего пользователя на уровне API/HTML/JS. По умолчанию — MemoryStore. Для PostgreSQL: `EPSILON_TEST_POSTGRES=1 node scripts/test-auth.mjs` — пустая одноразовая БД `epsilon_auth_test`; `EPSILON_TEST_POSTGRES=1 node scripts/test-organization.mjs` — отдельная пустая `epsilon_organization_test`. Обе — пользователь `epsilon_test`, `127.0.0.1:55439`. При наличии записей тест останавливается без перезаписи. Наборы проверены на локальной PostgreSQL 14.13; Compose использует PostgreSQL 16. Docker/production HTTPS проверяются при отдельном развёртывании.

HTML и ресурсы выдаются с `Cache-Control: no-store`. После публикации обновлений уже открытые вкладки нужно перезагрузить. Статический демонстрационный режим продолжает сохранять состояние в `localStorage`; авторизованное рабочее пространство не загружает пользовательский `localStorage` и получает задачи/права с сервера.

## Docker Compose / Dokploy

1. Используйте только отдельный проект, приложение и БД ЭПСИЛОН. Не читайте и не меняйте env других приложений. Укажите независимый доступ Dokploy при публикации.
2. Сохраните существующие `RND_CONTOUR_DB_*` ЭПСИЛОН; не пересоздавайте volume БД. Добавьте четыре `EPSILON_*` из приватной конфигурации. Ключ базы временных паролей храните вне БД и резервируйте отдельно; потеря ключа лишит возможности читать оставшиеся временные пароли (их можно перевыпустить). Bootstrap-хеш после первого успешного старта больше не используется для сброса.
3. Настройте сертификат и HTTPS-домен на сервис `web`, внутренний порт `8080`, `EPSILON_ORIGIN` — ровно этот HTTPS origin. Proxy должен перезаписывать `X-Forwarded-Proto` и `X-Forwarded-For`; порт 8080 и PostgreSQL не публикуйте напрямую. Не подключайте эту версию к прежнему открытому HTTP без настройки TLS.
4. Выполните `docker compose up --build` / deploy в отдельном приложении Dokploy. Проверьте `/healthz`, редирект с HTTP, сертификат, закрытие `/assets/seed.js` до входа, первый вход Суперадмина, создание тестового пользователя, смену пароля и повторный старт с сохранением учётных записей.

PostgreSQL не публикуется наружу. В этой версии она хранит авторизацию, серверный аудит и административные настройки в одной транзакционно блокируемой JSONB-записи. Это MVP на малую нагрузку: нормализация таблиц и нагрузочное тестирование нужны до масштабирования. Устаревшие сессии, лимиты и временные пароли очищаются при обработке запросов; политики резервирования и удаления старых копий настраиваются оператором.
